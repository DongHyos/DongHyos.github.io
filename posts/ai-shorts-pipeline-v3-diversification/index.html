상세한 프롬프트가 답은 아니었다 — AI 영상 주제 다양화 자동화 회고 (3편)

1편에서 AI 숏폼 자동화 파이프라인을 구축했고, 2편에서 영상 길이를 늘리려다 AI 영상 모델은 시간 순서를 모른다는 벽을 만났다. 이 글은 마지막으로 남은 가설 — 주제를 다양화하면 조회수가 오른다 — 를 자동화한 기록이자, 숏폼 시리즈를 닫는 글이다.

1. 문제 정의

2편 끝에서 두 개의 벽을 만났다. AI 영상 모델의 한계, 그리고 대량 업로드 뒤 노출이 떨어지는 알고리즘 함정. 조회수를 끌어올릴 카드로 주제 다양성 하나가 남아 있었다.

솔직히 고백하면, 당시 나는 알고리즘 벽을 뚫고 파이프라인을 고도화하고 싶었지만 무엇을 해야 할지 명확하지 않았다. 그래서 일단 손에 잡히는 것 — 주제를 늘리는 것 — 부터 했다. 지금 보면 이건 문제의 본질을 비껴간 선택이었고, 5장에서 다시 짚는다.

기술적 문제는 분명했다. PC 부품 청소 하나로 검증한 프롬프트 템플릿을, 유리 절단·보석·행성 단면 같은 전혀 다른 주제로 어떻게 옮길 것인가. 주제마다 1,000자가 넘는 프롬프트를 손으로 다시 쓰면 자동화의 의미가 사라진다.

2. 접근

주제 선정 — 시장조사와 감

주제를 무작정 늘리지 않았다. MCP(외부 도구를 모델에 연결하는 프로토콜) 검색으로 어떤 satisfying 주제에 수요가 있는지 조사하고, 거기에 감을 더해 후보를 좁혔다. 청소 계열을 넘어 절단(cutting) 계열로 축을 넓혔다 — 유리 과일, 보석, 행성 단면, 디저트, 음료.

형식의 발견 — 상세함의 함정

처음엔 더 상세하게 쓸수록 더 정확한 영상이 나온다고 가정했다. 1,000자가 넘는 정밀한 묘사를 프롬프트에 욱여넣었다.

결과는 반대였다. Veo 3는 과도하게 상세한 프롬프트를 소화하지 못하고 장면이 점프하거나 비현실적인 렌더를 냈다. 2편의 "시간 순서를 모른다"와 같은 계열의 문제다 — 모델은 텍스트를 인간처럼 축적해 읽지 않는다.

그래서 MCP로 Veo가 잘 이해하는 프롬프트 형식을 따로 조사했다. 핵심은 장황한 서술이 아니라 구조화된 핵심 요소의 나열에 가까웠다. 핵심 동작 하나, 매크로 렌즈, 9:16, 슬로모션, ASMR, 재질명 — 모델이 학습한 형식에 정렬된 간결한 프롬프트로 다시 쓰자 결과가 안정됐다. 여기서 자산화할 원칙 하나를 얻었다. 영상 생성 모델에선 프롬프트의 '상세함'이 아니라 '모델이 학습한 형식과의 정합성'이 품질을 결정한다.

자동화 문제 — 형식을 13주제로 복제

검증된 형식을 13개 주제로 퍼뜨려야 했다. 그런데 사람이 손으로 다시 쓰면 자꾸 디테일을 더해 방금 검증한 형식이 무너진다. 상세함의 함정에 다시 빠지는 것이다. 그래서 변형을 LLM에게 맡기되, 형식은 보존하고 주제 어휘만 바꾸도록 가드레일을 치기로 했다. 이것이 PromptDiversifier다.

3. 구현 — PromptDiversifier

세 가지 장치로 설계했다. (사이드 프로젝트 코드에서 핵심 패턴만 추린 재구성 예제다.)

(1) 보존/변형 계약

시스템 프롬프트로 LLM에게 무엇을 바꾸지 말고 무엇을 바꿀지를 명시한다. 이 계약이 형식의 척추를 지킨다.

REPHRASE_SYSTEM_PROMPT = """\
You are a video-prompt rephrasing assistant.
MUST preserve: main subject, core action, macro lens, 9:16 aspect ratio,
  slow motion, ASMR audio, material names (glass, crystal).
NEVER change the action type (cutting -> cleaning, or vice versa).
VARY: sentence structure, adjectives, descriptive order.
Keep a similar length and the same language as the input.
{topic_rules}
"""

{topic_rules}에는 주제별로 반드시 살려야 할 요소를 끼워 넣는다(예: 절단 주제라면 "knife, cross-section reveal").

(2) 검증 게이트

LLM은 계약을 어길 수 있다. 그래서 변형 결과에 주제별 필수 키워드가 살아남았는지 검사하고, 빠졌으면 채택하지 않고 원본으로 되돌린다.

async def diversify_prompt(self, prompt: Prompt) -> Prompt:
    """형식은 보존하고 주제 어휘만 바꾼다. 어느 단계에서 실패하든 원본으로 안전 복귀한다."""
    if not self.enabled:
        return prompt  # ① 비활성 → 변형을 건너뛰고 원본 그대로

    try:
        rephrased = await self._call_llm(REPHRASE_SYSTEM_PROMPT, prompt.text)

        # ② 검증 게이트: 주제의 핵심 키워드가 변형 후에도 남아 있는가
        required = TOPIC_REQUIRED_KEYWORDS.get(prompt.template_id, [])
        if any(kw not in rephrased.lower() for kw in required):
            logger.warning("형식 이탈(키워드 누락) → 원본 유지")
            return prompt  # ③ 검증 실패 → 원본으로 fallback

        return replace(prompt, text=rephrased, original_text=prompt.text)
    except Exception as exc:
        logger.warning(f"변형 호출 실패 → 원본 유지: {exc}")
        return prompt  # ④ API 오류·예외 → 원본으로 fallback

이 게이트가 실제로 막아준 사례가 있다. LLM이 다양화 과정에서 cutting을 cleaning으로 바꾸거나 매크로·ASMR 같은 형식 요소를 슬쩍 떨어뜨린 결과를 내놓을 때, 키워드 검사가 그것을 걸러 원본으로 되돌렸다.

(3) 다층 fallback

자동화 파이프라인에서 한 단계의 LLM 실패가 전체를 멈추면 안 된다. 그래서 비활성·API 오류·검증 실패 어느 경우든 원본 프롬프트로 안전하게 떨어지게 했다. 다양화는 덤이지 파이프라인의 필수 의존이 아니라는 설계 원칙이다.

이 세 장치 덕분에 사람이 손대지 않고 프롬프트를 13개 주제로 복제했다. 한 파이프라인이 같은 형식을 공유하며 만든 결과물이다.

같은 파이프라인·같은 형식으로 만든 서로 다른 네 주제(유리 행성·보석·디저트·음료 단면). 주제 어휘만 바뀌고 매크로·슬로모션·ASMR 형식은 동일하다.

4. 결과

정량적으로는 성공했다. 주제 1개(PC 부품 청소)에서 13개로, 누적 201편을 사람의 프롬프트 재작성 없이 생성했다. 청소 계열(초음파·레이저·먼지)과 절단 계열(유리·보석·행성·디저트·음료·한식)로 폭이 넓어졌다.

그러나 노출은 그대로였다. 주제를 13배로 늘렸지만 조회수와 추천 노출에 의미 있는 변화가 없었다. 2편에서 만난 노출의 벽은 주제 다양성으로는 뚫리지 않았다.

5. 학습

이 시도에서 세 가지를 배웠다.

첫째, 영상 모델에선 '상세함'이 아니라 '형식 정합성'이 레버다. 1,000자 정밀 묘사가 8초를 망쳤고, 모델이 학습한 형식에 맞춘 간결하고 구조화된 프롬프트가 살렸다. 2편의 "시간 순서를 모른다"와 합치면 하나의 원칙이 된다 — 영상 생성 모델은 인간의 글쓰기 직관과 다른 입력 형식을 요구한다. 더 길게·더 자세히가 아니라 모델의 형식에 맞게.

둘째, LLM을 생성 루프에 넣을 땐 '보존 계약 + 검증 게이트 + fallback'이 필수다. LLM에게 변형을 맡기는 순간 형식이 무너질 위험이 생긴다. 무엇을 보존할지 계약으로 못 박고, 결과를 게이트로 검증하고, 실패 시 원본으로 안전하게 되돌리는 3종 가드레일은 영상 프롬프트뿐 아니라 LLM이 기존 산출물을 변형하는 모든 자동화에 그대로 옮길 수 있다. 이 시리즈에서 가장 재사용성 높은 자산이다.

셋째, '주제 수'는 알고리즘 벽의 레버가 아니었다. 가장 뼈아픈 학습이다. 무엇을 해야 할지 몰라 움직이기 쉬운 변수(주제 늘리기)부터 당겼지만, 그건 결과를 움직이는 변수가 아니었다. 내 경우 노출에 더 크게 작용한 변수는 2편에서 본 업로드 양과 채널의 신뢰도로 보였다(플랫폼 노출 정책은 비공개이므로 단일 사례의 관찰이다). 자동화로 쉬운 변수를 13배 늘리는 일과, 결과를 실제로 움직이는 일은 달랐다.

숏폼 파이프라인은 여기서 일단락한다. 1편의 자동화 가설은 검증됐고, 2편·3편에서 품질·길이·주제 세 레버를 모두 당겨봤지만 노출의 벽은 끝내 넘지 못했다. 이 실험과 병렬로 나는 롱폼 영상 파이프라인을 따로 돌리고 있었다. 숏폼을 접고 롱폼으로 옮겨간 것이 아니라, 세 편에 걸쳐 숏폼의 한계를 체감하면서 무게중심이 자연스럽게 롱폼으로 기울었다.

숏폼 3부작을 한 줄로 닫는다. 자동화의 진짜 가치는 '많이 만드는 것'이 아니라 '검증된 형식을 안전하게 반복하는 것'이었다. 다음 시리즈에서는 그 무게가 옮겨간 곳 — 풀스택 롱폼 파이프라인 — 을 다룬다.
