LLM에게 주문을 맡기지 않았다 — 안전 경계를 프롬프트가 아니라 코드에 두기

이 글은
  • 다루는 문제: LLM에게 매매 판단을 맡기면서, 어떻게 폭주(오발주)를 구조적으로 막는가
  • 접근: 결정론 안전 코어와 확률 조언 레이어를 분리하고, 안전 경계를 프롬프트가 아니라 코드에 둔다

"AI 자동매매"가 무서운 건 LLM이 멍청해서가 아니다

토스증권이 OPEN API로 주문 실행까지 열어주면서, 나는 개인 계좌로 도는 자동매매 시스템을 만들기 시작했다. 뉴스를 읽고 매매 후보를 추리는 판단에는 LLM을 쓰고 싶었다. 문제는 그다음이다. LLM에게 "이 종목 사"라고 주문까지 맡기는 순간, 시스템의 안전은 LLM이 실수하지 않는다는 가정 위에 선다.

그 가정은 위험하다. LLM은 비결정적이다. 같은 입력에 다른 출력을 낼 수 있고, 프롬프트 인젝션이나 가짜 뉴스에 휘둘릴 수 있다. 반면 주문은 비가역적이다. 일단 체결되면 되돌릴 수 없고, 그 대상이 실제 돈이다. 비결정적인 판단기에 비가역적인 권한을 직접 쥐여주는 것, 이것이 "AI 자동매매"라는 말이 주는 공포의 정체다.

흔한 접근은 프롬프트로 안전을 거는 것이다. "절대 하루 50만 원 넘게 주문하지 마", "확실하지 않으면 사지 마" 같은 지침을 시스템 프롬프트에 박는다. 하지만 이건 안전 경계를 LLM의 순응에 의존하게 만든다. 경계가 코드가 아니라 자연어 부탁에 있다. 나는 이 구조를 택하지 않기로 했다. 설계 문서에 남긴 첫 거부 결정이 이것이다. "LLM 중심 오케스트레이션은 안전 경계가 프롬프트에 의존하므로 폭주 위험이 있다."

접근: 똑똑한 층과 안전한 층을 분리한다

내가 세운 제1원칙은 수익이 아니라 오발주 회피다. "틀린 행동보다 무행동이 낫다. 의심스러우면 멈춘다." 이 원칙을 코드로 강제하려면, 돈을 만지는 결정과 LLM의 판단을 같은 곳에 두면 안 된다.

그래서 시스템을 두 레이어로 쪼갰다.

  • 확률 레이어(조언자): LLM이 뉴스를 읽고 위키를 갱신하고 매매 규칙을 제안한다. 비결정적이고, 틀릴 수 있는 층.
  • 결정론 코어(엔진, 케이지, 게이트웨이): 규칙을 평가하고 한도를 검사하고 실제 주문을 낸다. 재현 가능하고, LLM이 없어도 도는 층.

핵심은 두 층 사이의 경계다. 확률 레이어는 결정론 코어에 제안을 흘려보낼 수 있을 뿐, 코어를 직접 움직일 수 없다. 그리고 그 경계는 프롬프트가 아니라 코드와 타입으로 강제된다.

이 그림에서 LLM(조언자)부터 토스 API까지 직선이 없다는 점이 전부다. 모든 경로는 사람의 승인을 거치고, 모든 주문은 케이지라는 단일 관문을 통과한다.

구현: LLM이 닿을 수 없는 경계

경계를 네 겹으로 세웠다.

1. 조언자는 매매 코어를 import조차 못 한다. 조언자 모듈은 토스 게이트웨이, 케이지, 엔진, 주문 상태 저장소를 import하지 않는다. 코드에서 그 심볼에 접근할 방법이 아예 없다. 이건 주석에 적은 약속이 아니다. 테스트가 조언자의 import 그래프를 AST로 훑어, 토스나 코어가 끼어들면 실패하도록 강제한다. 조언자가 할 수 있는 건 저장소에 규칙을 제안하는 것뿐이다.

2. 제안과 승인을 호출자로 격리한다. 규칙 저장소는 모든 호출에 "누가 부르는지"를 함께 받는다.

class Caller(Enum):
    ADVISOR  = "advisor"   # 조언자(LLM) — 제안(propose)만
    USER_CLI = "user_cli"  # 사람 — 승인(transition)만
    ENGINE   = "engine"    # 엔진 — active 규칙 읽기만

def propose_rule(self, draft: RuleDraft, *, caller: Caller) -> str:
    if caller is not Caller.ADVISOR:
        raise CallerNotAuthorizedError("proposeRule은 조언자만 호출할 수 있다")
    # 생성 상태는 항상 proposed로 고정. active로 만들 인자가 이 함수에 없다.
    return self._insert(draft, state=RuleState.PROPOSED)

def transition(self, rule_id, action, *, caller: Caller) -> RuleState:
    if caller is not Caller.USER_CLI:          # 조언자의 자가 승인을 차단
        raise CallerNotAuthorizedError("transition은 사람/CLI만 호출할 수 있다")
    ...

조언자(LLM)는 propose_rule만 부를 수 있고, 이 함수에는 규칙을 active로 만들 인자가 존재하지 않는다. 생성 상태는 언제나 proposed로 고정된다. 그리고 proposed를 active로 올리는 transition은 사람만 부를 수 있다. LLM이 제안한 규칙은 사람이 승인하기 전까지 거래에 쓰이지 않으며, LLM이 자기 제안을 스스로 승인하는 통로는 코드에 없다. 자동 실행과 자동 규칙 변경은 다른 문제다. 규칙이 바뀌는 자리에는 반드시 사람이 든다.

3. 추론은 규칙으로 박제돼 들어온다. 사람이 승인한 규칙의 발화 조건(trigger)은 LLM이 매 순간 판단하는 게 아니라, 이런 JSON 조건으로 굳어 있다.

# 사람이 승인한 규칙의 trigger. 엔진은 이것을 결정론으로 평가할 뿐,
# 평가 시점에 LLM을 호출하지 않는다.
{"all": [
    {"type": "schedule", "date": "2026-09-15", "within_days": 3},  # 예정 이벤트 임박
    {"type": "price",    "op": "<=", "value": "70000"}             # 가격 눌림목
]}

def _evaluate_trigger(self, rule, now) -> bool:
    try:
        return self._eval_spec(json.loads(rule.trigger), rule, now)
    except Exception:
        # 파싱 실패·미지원 신호·시세 누락 등 평가 불가는 전부 미충족(무발주).
        # 제1원칙: 모르면 멈춘다. "모르니 일단 발주"는 없다.
        return False

엔진은 active 규칙만 읽어 이 조건을 평가한다. 매매 루프 어디에도 LLM 호출이 없다. LLM의 판단은 사람의 승인을 거쳐 정적인 규칙으로 굳은 뒤에야 코어에 들어오고, 굳은 뒤에는 더 이상 비결정적이지 않다. 평가가 조금이라도 불확실하면 엔진은 무발주를 택한다(fail-closed).

4. 모든 주문은 케이지라는 단일 관문을 통과한다. 엔진조차 게이트웨이를 직접 참조하지 않는다. 주문은 오직 케이지의 submit으로만 나간다. 케이지는 kill 스위치, 종목 화이트리스트, 금액·횟수 한도, 멱등(중복 방지)을 차례로 검사하고, 어느 조회든 실패하면 보수적으로 거부한다. 그리고 실제 주문 전송은 모드가 LIVE일 때만 일어난다. 기본값은 판단만 하고 주문은 내지 않는 SHADOW다.

결과: 경계를 코드로 증명한다

이 구조의 값어치는 "안전하게 짰다"는 주장이 아니라, 경계가 코드로 증명된다는 데 있다.

  • 조언자의 import 그래프에 토스와 코어가 0임을 AST 테스트가 강제한다. 이런 경계 가드는 금지된 import를 일부러 주입했을 때 실제로 실패하는 것까지 확인했다.
  • 같은 규칙이 같은 날 반복 충족돼도 멱등키로 중복 주문이 0이다.
  • 안전 이음매에 결함을 일부러 심었을 때 해당 테스트가 깨지는지 역으로 확인했다. 모드 게이트를 무력화하면 SHADOW에서도 주문이 나가고, 멱등 가드를 무력화하면 중복 주문이 생기는 식이다. 통과가 헛통과가 아님을 보장하기 위해서다.
  • 전체 447개 테스트가 통과하고, 외부 의존성이 0이다(표준 라이브러리만). LLM SDK조차 import하지 않는다.

정직하게 적자면, 이 시스템은 아직 SHADOW 단계다. 실주문은 0건이고, 따라서 수익률 같은 건 이 글에서 주장하지 않는다. 애초에 이 글의 주제도 아니다. 내가 증명하려 한 건 "돈을 벌었다"가 아니라 "LLM이 폭주해도 돈에 닿지 못한다"는 구조이며, 그 구조는 실거래 이전에 코드와 테스트로 증명되는 종류의 것이다.

학습

첫째, 안전 경계는 프롬프트가 아니라 코드에 있어야 한다. "~하지 마"라고 부탁하면 LLM이 따라줄 때만 안전하다. import 불가, 함수 인자 부재, 호출자 격리처럼 타입과 구조로 막으면 LLM이 무엇을 출력하든 경계가 유지된다. 전자는 가정이고 후자는 보장이다.

둘째, LLM을 똑똑하게 만드는 일과 LLM을 가두는 일은 다르다. 나는 조언자의 추론 품질을 높이는 데 시간을 거의 쓰지 않았다. 실제 LLM 호출은 의도적으로 보류하고 안전 골격을 먼저 세웠다. 위험한 건 멍청한 LLM이 아니라, 똑똑하든 멍청하든 주문 버튼에 직접 닿는 LLM이다. 가두는 일이 똑똑하게 만드는 일보다 먼저다.

셋째, 이 패턴은 자동매매만의 것이 아니다. 비가역적이고 권한이 큰 작업, 이를테면 결제, 배포, 데이터 삭제에 LLM 에이전트를 붙일 때 같은 구조가 쓰인다. LLM은 제안하게 하고, 실행 권한은 결정론 코드 게이트에 두고, 그 사이에 사람의 승인을 끼운다. 에이전트에 권한을 위임하는 시대에, 위임의 안전은 결국 "에이전트가 닿을 수 없는 경계를 코드로 어디에 그었는가"로 결정된다.
