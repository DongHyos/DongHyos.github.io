사실은 기계가 뽑고 규범은 사람이 정한다 — LLM이 프로젝트를 모를 때 무엇을 채웠나

돌아가는데 이 프로젝트 것이 아니다

구현을 맡기면 세 가지가 반복됐다.

첫째, 프로젝트에 안 맞는 방식으로 짰다. 이름 짓기와 레이어 배치, 오류 처리 방식이 기존 관행과 어긋났다. 이미 있는 공용 컴포넌트를 쓰는 방법도 달랐다.

둘째, 이미 있는 함수를 다시 만들었다. 구현 전에 비슷한 함수가 어디 있는지 확인하지 못했다. 리뷰에서 중복을 발견해도 이미 코드를 작성한 뒤였고, 놓친 중복은 그대로 남았다.

셋째, 시키지 않은 파일까지 건드렸다. 요청한 것은 한 기능인데 손댄 범위가 그보다 넓었다.

이 문제는 코드의 실행 여부만으로는 드러나지 않는다. 컴파일과 테스트를 통과해도 기존 구조와 어긋나 리뷰에서 되돌아오는 경우가 있었다. 요청 범위를 넘긴 변경 역시 기능 테스트만으로는 걸러지지 않았다.

「모른다」가 한 종류가 아니었다

한동안 이걸 하나의 문제로 봤다. LLM이 컨텍스트를 모르니 컨텍스트를 주면 된다는 식이었다. 그런데 셋을 나란히 놓으니 모르는 대상이 서로 달랐다.

안 맞는 방식으로 짬   →  이 프로젝트가 어떻게 쓰는지 모름   =  규범을 모름
이미 있는 걸 또 만듦  →  무엇이 어디 있는지 모름            =  사실을 모름
시키지 않은 곳을 건듦 →  이 작업이 어디까지인지 모름        =  범위를 모름

가르고 나니 확인할 곳이 달라졌다. 기존 함수의 위치와 호출 관계 같은 구현 사실은 코드에서 확인한다. 반면 코드에 관찰된 관행을 앞으로 지킬 규범으로 삼을지는 사람이 결정해야 한다. 변경 범위는 요청과 기존 구조를 함께 대조해 정한다.

현황 지도와 규약을 여섯 단계 안에 넣지는 않았다. 작업마다 처음부터 새로 만들 문서가 아니라 프로젝트에 남겨 두고 갱신할 문서이기 때문이다. 두 문서는 여섯 단계 바깥에 두고 필요한 단계가 입력으로 읽도록 했다.

사실은 기계가 뽑는다

현황을 추출하는 스킬을 따로 뒀다. 에이전트가 코드베이스를 읽고 개요·구조·컴포넌트·API·데이터를 문서화한다. 규율은 코드에서 관찰된 사실에 근거를 붙이고, 확인하지 못한 항목은 「미확인」으로 표시하는 것이다. 문서가 코드와 계속 일치하는지는 갱신할 때 다시 대조해야 한다.

두 가지를 다르게 했다.

하나는 기능 단위로 묶은 것이다. 컴포넌트·API·데이터를 기술 레이어별로 흩어 놓으면, 「이 기능이 무엇을 건드리는가」를 보려고 여러 문서를 오가야 한다. 기능 변경의 영향을 한곳에서 확인하도록 문서를 기능별로 모았다. 기능별 문서를 읽고 구현을 시작하니 기존 함수와 관련 파일을 찾기 쉬웠다.

다른 하나는 갱신 경로를 작업 흐름에 연결한 것이다. 코드가 바뀌면 현황 지도도 낡을 수 있다. 당시 파이프라인은 작업 완료 뒤 지도 갱신을 제안했다. 현황 추출 스킬을 다시 실행하면 관련 부분만 증분으로 스캔하는 방식이었다. 제안만으로 갱신이 완료되는 것은 아니므로, 다음 작업에서 지도를 믿기 전에 변경분이 반영됐는지 확인해야 한다.

요청 범위를 볼 때도 기능별 지도가 도움이 됐다. 변경 요청을 지도와 실제 코드에 대조하면 관련 파일의 후보를 좁힐 수 있다. 지도가 요청 자체의 경계를 결정하거나 불필요한 수정을 자동으로 막는 것은 아니다.

규범은 사람이 정한다

규약은 다르게 다뤘다. 코드에서 관찰된 관행을 후보로만 제시하고, 확정은 사람 승인을 받는다. 관찰만으로 자동 확정하지 않는다.

이유는 단순하다. 코드에 있는 것은 관행이지 규범이 아니다. 코드에는 좋은 패턴과 나쁜 패턴이 같이 있고 어느 쪽을 표준으로 삼을지는 코드가 답하지 못한다.

규약끼리 모순되지 않아야 한다는 조건도 걸었다. 전역 규칙과 주제별 세부가 같은 대상을 다르게 규정하면 적용 기준이 흔들린다. 새 규약이 기존 규약과 부딪히면 확정 전에 해소하도록 했다.

형식에도 조건을 걸었다. 「깔끔하게 짜라」 같은 문장은 규약으로 받지 않는다. 무엇을 어떻게 하는지 확인할 기준과 예시가 있어야 다음 단계에서 적용 여부를 판단할 수 있다.

나쁜 관행을 규약으로 받아들였다

여기서 예상과 다른 판단을 했다.

한 프로젝트의 프런트엔드에서 React 훅 사용과 상태 관리가 어그러져 있었다. 규약을 세울 차례였고, 나는 그 부분을 현재 소스 그대로 규약에 적었다. 나쁜 줄 알면서 그렇게 적었다.

이상적인 방식을 곧바로 규약에 적으면 이후 코드만 새 기준을 따르고 기존 코드는 그대로 남는다. 같은 기능 안에서 상태 관리 방식이 갈릴 수 있었다. 나는 당시 코드와의 정합성을 우선하고, 리팩토링할 때 기준을 바꾸기로 했다.

리팩토링에 착수하면서 규약에 새 기준을 먼저 적고 그 기준에 맞춰 소스를 바꿨다. 규약 변경은 코드 변경의 기준을 명시하는 역할을 했다.

규약을 프로젝트가 현재 따르기로 한 기준으로 삼았다. 바꾸고 싶은 방향을 적어 두는 문서와는 용도가 다르다. 리팩토링에서는 규약과 코드를 같은 변경 범위에서 함께 옮겨야 한다.

결과, 그리고 대가

현황 쪽에는 전체 개요와 구조, 기능별 문서가 생겼다. 규약 쪽에는 전역 규칙과 주제별 문서가 생겼다. 주제는 프로젝트에 따라 이름 짓기·오류 처리·피해야 할 패턴 등으로 나뉜다.

사용하면서 앞의 세 실패가 덜 반복된다고 관찰했지만, 리뷰 지적 횟수나 재작업 시간을 비교해 두지는 않았다. 이 경험만으로 문서가 원인이라고 확정하거나 효과의 크기를 말할 수는 없다. 확인 가능한 결과는 구현 전에 기존 기능의 위치와 승인된 규약을 읽을 수 있게 됐다는 점이다.

대가도 남았다. 당시의 어그러진 관행을 규약으로 받아들인 만큼, 새 코드도 그 방식을 따를 수 있었다. 리팩토링 전까지는 그 위험을 감수하는 선택이었다. 현재 코드와의 정합성을 우선한 판단이 항상 옳다는 뜻은 아니다. 오래 유지할 규약이라면 관행을 받아들이는 시점에 언제 다시 바꿀지도 정해야 한다.

학습

  • 모르는 대상을 먼저 구분한다. 기존 구현은 코드에서 확인하고, 앞으로 지킬 규칙은 사람이 승인하며, 변경 범위는 요청과 코드 구조를 대조해 정한다.
  • 코드에 있는 것은 관행이지 규범이 아니다. 관찰한 패턴을 그대로 표준으로 굳히면 나쁜 관행까지 강제가 된다. 관찰은 후보를 만드는 데까지고 결정은 사람 몫이다.
  • 규약은 현재 합의한 기준으로 쓴다. 목표 상태를 적는 것과 구분하고, 리팩토링할 때는 규약의 새 기준과 코드 변경을 함께 검토한다.
  • 현황 지도의 갱신 여부를 확인한다. 작업 완료 뒤 갱신을 권하고 변경분 재스캔 경로를 둬도 자동 갱신은 아니다. 다음 작업에서 문서를 쓰기 전에 코드와 일치하는지 대조해야 한다.
