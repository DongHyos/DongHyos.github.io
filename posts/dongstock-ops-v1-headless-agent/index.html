무인 에이전트에게 셸을 주지 않았다 — 스케줄 위 LLM을 돈에서 떼어놓고 살려두기

이 글은
  • 다루는 문제: 매일 뉴스·촉매 델타를 LLM에게 무인으로 수집시키고 싶다. 그런데 스케줄 위에서 도는 LLM 에이전트는 두 가지가 무섭다. 돈줄(주문, 키, 셸)에 닿는 것, 그리고 잠자기, 인증, 네트워크에 조용히 죽는 것
  • 접근: LLM SDK를 매매 코드에 배선하지 않고 CLI를 launchd가 별도 프로세스로 실행한다. 권한은 프롬프트가 아니라 OS 레이어에서 최소화하고, 산출물은 드래프트로 격리해 사람이 병합한다. 무인 견고성은 낙관이 아니라 방어로 만든다
  • 결과·학습: 실제로 launchd로 도는 파이프라인과, 잠자기·토큰 만료와 싸운 로그. 무인 에이전트의 안전은 프롬프트가 아니라 OS 권한 경계에 있고, 스케줄 프로세스의 진짜 적은 로직이 아니라 환경이다
  • 도움 되는 독자: LLM 에이전트를 무인·주기 실행으로 돌리려는데, 그 에이전트가 민감한 자원에 닿지 않게 하고 싶은 개발자

기계가 만드는 재료, 사람이 당기는 방아쇠

이 자동매매 시스템에는 뉴스·촉매를 누적하는 지식층이 있다. 매일 이 지식층에 시장 델타를 급유해야 하는데, 사람이 하루 세 번 전 섹터 뉴스를 훑는 일은 지속되지 않는다. LLM에게 맡기는 게 자연스럽다. 그런데 이걸 무인으로, 스케줄로 돌리는 순간 두 가지 공포가 생긴다.

첫째, 무인 LLM이 무엇에 닿는가. 이 시스템은 실주문을 낼 수 있는 코드(케이지·게이트웨이)와 브로커 API 키를 갖고 있다. 사람 없이 스케줄로 도는 에이전트가 그 표면에 조금이라도 닿을 수 있으면, 내가 자리를 비운 사이 무슨 일이든 일어날 수 있다. 1편에서 안전 경계를 프롬프트가 아니라 코드에 뒀다고 했는데, 무인 에이전트에서는 그 경계가 한층 더 엄격해야 한다.

둘째, 무인 프로세스는 조용히 죽는다. 노트북에서 launchd로 도는 잡은 잠자기, 네트워크, 인증 만료에 취약하고, 죽어도 아무도 즉시 보지 못한다. 매끄럽게 도는 데모를 만드는 것과, 사람이 안 보는 몇 주 동안 실제로 도는 잡을 만드는 것은 다른 문제다.

접근: 별도 프로세스 + OS 권한 최소화 + 방어적 견고성

두 축으로 결정했다.

격리 축. LLM을 매매 코드에 배선하지 않는다. LLM SDK를 엔진이나 케이지가 import하는 순간, LLM과 돈줄이 같은 프로세스에 산다. 대신 claude CLI를 launchd가 별도 프로세스로 실행한다. LLM은 매매 코드와 주소 공간을 공유하지 않는다. 이 시스템의 매매 루프에는 런타임 LLM 호출이 0인데(1편), 무인 지식 수집도 같은 원칙을 따른다. LLM은 프로세스 밖에서 재료만 만든다.

생존 축. 무인 견고성은 낙관이 아니라 방어로 만든다. 잠자기, 인증 만료, 네트워크 지연은 "혹시"가 아니라 "반드시" 일어난다고 보고 대비한다.

이 자동화 레이어에는 잡이 하나 더 있다. 파이썬 모니터가 장중 전 시장을 스캔해 진입 후보 도달 시 macOS 알림만 쏜다(주문은 0). LLM 델타든 파이썬 모니터든 규율은 같다. 자동은 재료를 만들고, 방아쇠는 사람이 당긴다.

구현 1 — 격리: 권한을 OS에서 최소화한다

claude -p(헤드리스)를 --permission-mode dontAsk로 띄운다. 이 모드에서는 허용 목록에 없는 모든 도구·경로가 프롬프트 없이 자동 거부된다. 그래서 보안의 핵심은 좁은 허용 화이트리스트다.

// 무인 루틴 권한 스코프 (settings.json 발췌)
{
  "permissions": {
    "allow": [
      "Read(~/project/dong-stock/**)",
      "Write(~/project/dong-stock/wiki/news/**)",
      "Edit(~/project/dong-stock/wiki/news/**)",
      "mcp__tavily__search",
      "mcp__exa__search"
    ],
    "deny": [
      "Bash",
      "Read(~/.toss.env)",   // 브로커 API 키
      "Read(~/.env)",
      "Read(~/.claude/**)"
    ]
  }
}

읽기는 프로젝트 안으로, 쓰기는 위키 디렉토리로만 연다. 검색 MCP는 허용하되, 셸(Bash)과 브로커 키 파일은 명시적으로 거부한다. 무인 에이전트가 임의 명령을 실행하거나 키를 읽을 통로가 원천 차단된다.

여기서 실측으로 배운 함정이 하나 있다. deny가 allow를 이긴다. bare Write나 Edit를 deny에 넣으면 위키 쓰기 허용까지 함께 죽어 에이전트가 아무것도 쓰지 못한다. 그래서 셸과 시크릿은 도구·경로 단위로 좁게 거부하고, 넓은 쓰기 거부는 두지 않는다. 최소권한은 "많이 막기"가 아니라 "정확히 막기"였다.

실행 플래그에도 하드 가드를 한 겹 더 건다.

claude -p "$PROMPT" --permission-mode dontAsk --disallowedTools "Bash,Edit"

--disallowedTools "Bash,Edit"로 기존 파일 편집과 임의 실행을 한 번 더 막는다. 그 결과 무인 실행이 할 수 있는 일은 새 드래프트 파일 쓰기, 읽기, 검색뿐이다. 산출물은 날짜별 드래프트 파일로만 떨어지고, 정식 지식 체인에 반영하는 일은 다음 날 아침 사람이 검토해 병합한다. 자동은 드래프트를 쓰고, 판단과 반영은 사람이 한다.

구현 2 — 생존: 무인 프로세스를 살려두기

launchd plist가 매일 정해진 시각에 발화해 run_delta.sh를 부르고, 스크립트가 요일로 모드를 정한다(평일 얕게 여러 번, 토요일 깊게, 일요일 휴식). 여기까지는 쉽다. 어려운 것은 무인 견고성이다. 세 가지를 방어했다.

첫째, 네트워크 대기. 노트북이 자다 깨어 launchd가 잡을 실행하면, 네트워크 스택이 아직 안 올라와 첫 요청이 ENOTFOUND로 죽는다. 그래서 실제 작업 전에 API 도달을 최대 5분간 폴링한다.

for _ in $(seq 1 30); do
  curl -s -m 5 -o /dev/null https://api.anthropic.com && { NET_OK=1; break; }
  sleep 10
done
[ "$NET_OK" = 1 ] || { echo "네트워크 미준비 — 중단"; exit 1; }

둘째, 자작 워치독. macOS에는 timeout(coreutils) 명령이 없다. 무인 잡이 hang하면 몇 시간이고 매달린다. 그래서 백그라운드 실행과 별도 kill 타이머로 15분 상한을 직접 구현했다.

caffeinate -i "$CLAUDE" -p "$PROMPT" ... &   # caffeinate = 실행 중 잠자기 억제
pid=$!
( sleep 900; kill "$pid" 2>/dev/null ) &     # 15분 뒤 강제 종료
wd=$!
wait "$pid"; rc=$?
kill "$wd" 2>/dev/null

caffeinate -i는 3편에서 손절 폴링을 위해 쓴 것과 같은 도구다. 실행 중 절전으로 빠지면 인증이 잠기거나 잡이 멈추므로, 실행하는 동안만 잠자기를 억제한다.

셋째, 재시도. 일시적 인증·네트워크 실패를 60초 간격으로 최대 세 번 흡수하고, 성공하면 즉시 빠져나온다. 그리고 이 스케줄은 구독 인증으로 도는데, 이 인증은 API 종량과금이 아니라 사용량 한도만 차감한다. 대신 토큰이 만료되면 조용히 실패하므로, 로그를 진실의 원천으로 삼아 가끔 확인한다.

결과: 실제로 돌지만, 정직하게 완벽하진 않다

이 파이프라인은 지금 실제로 launchd로 돈다. 그런데 로그는 그 과정이 매끄럽지 않았음을 정직하게 보여준다. 아래는 전략 내용을 걷어낸 인프라 라인만 추린 것이다.

[06-29 08:11] delta 시작 → 401 authentication_error   (구독 토큰 만료)
[06-30 16:35] delta 시작 → ENOTFOUND                  (자다 깬 직후)
   ── 네트워크 대기 · 워치독 · 재시도 하드닝 추가 ──
[07-01 20:49] delta 종료(exit 0)                      (첫 성공)
[07-06 20:03] 시도 3/3 → 완료(exit 0)                 (재시도가 흡수)
[07-10 18:13] 시도 2/3 → exit 143                     (워치독이 hang을 kill)
[07-10 23:07] 시도 3/3 → 종료(exit 0)

하드닝을 넣기 전(6/29~7/1)에는 401, ENOTFOUND, 타임아웃으로 거의 매번 죽었다. 네트워크 대기, 워치독, 재시도를 넣은 뒤 첫 성공이 떴고, 이후로는 재시도가 실패를 흡수해 exit 0에 도달하는 날이 늘었다. exit 143은 워치독이 hang한 시도를 SIGTERM으로 끊은 흔적이다. 설계대로 동작한 실패다.

정직하게, 완전히 근절되지는 않았다. 잠자기가 깊은 날은 세 번의 재시도가 다 네트워크를 못 잡아 그날 델타를 건너뛴다. 무인 스케줄이 노트북 위에 있는 한, 이것은 3편의 SPOF와 같은 뿌리, 곧 기계가 깨어 있어야 한다는 제약을 공유한다. 그래서 이 델타는 있으면 좋은 재료이지, 없으면 매매가 멈추는 의존이 아니게 설계했다. 실패해도 그날 아침 병합할 드래프트가 하나 비는 것뿐이다.

학습

첫째, 무인 에이전트의 안전은 프롬프트가 아니라 OS 권한 경계에 있다. "위험한 짓 하지 마"라고 프롬프트에 적는 것은 에이전트의 순응에 기대는 안전이다. 무인으로 도는 에이전트에서는 그 기대가 위험하다. 대신 허용 화이트리스트와 거부 목록으로 도구·경로를 OS 레이어에서 잠그면, 에이전트가 무엇을 하려 하든 돈줄에 닿을 통로 자체가 없다. 1편에서 안전을 코드에 뒀던 원칙이, 무인 에이전트에서는 OS 권한 경계로 확장된다.

둘째, 스케줄 위 프로세스의 진짜 적은 로직이 아니라 환경이다. 정상 경로를 처리하는 코드는 몇 줄이면 되지만, 잠자기에서 깨어난 순서, 인증 만료, 네트워크 미준비를 견디는 코드가 스크립트의 대부분을 차지했다. 무인 자동화의 난이도는 "무엇을 하는가"가 아니라 "사람이 안 볼 때 어떻게 죽고 어떻게 되살아나는가"에 있었다.

셋째, 자동화의 산출은 결정이 아니라 재료로 둔다. 드래프트 전용 격리와 아침 병합은 번거롭지만, 이 번거로움이 무인 LLM을 안전하게 만든다. 자동이 드래프트를 쌓고 사람이 판단을 얹는 경계는, 되돌릴 수 없는 행동을 다루는 모든 자동화에 일반화된다.
