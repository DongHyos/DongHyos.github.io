테스트가 운영 DB를 오염시켰다 — 공용 DB를 버리고 Testcontainers 격리로

이 글은
  • 다루는 문제: 공용 DB로 통합 테스트를 돌리다, 테스트 데이터가 운영으로 새어 들어갔다.
  • 접근: 각 테스트에 격리된 일회용 DB를 주는 Testcontainers를 도입하고, Restarted·Shared 격리 전략을 비교했다.
  • 결과·학습: 테스트를 운영에서 떼어냈다. 완전 격리(Restarted)와 속도(Shared)의 트레이드오프에서 Shared를 택하되, 그 함정을 코드로 확인하고 들어갔다.
  • 도움 되는 독자: 통합 테스트의 DB 격리·멱등성을 고민하는 백엔드 개발자.

문제: 테스트가 운영 데이터를 오염시켰다

통합 테스트를 공용 개발 DB에 직접 붙여 돌리고 있었다. 공용 DB는 통합 테스트의 흔한 출발점이다. 운영과 같은 DB 엔진을 쓰니 별도 환경을 꾸릴 필요가 없기 때문이다. 테스트는 실제 테이블에 데이터를 넣고 조회했고, 그 데이터는 테스트가 끝나도 DB에 남았다.

문제는 이 개발 DB의 데이터를 운영으로 옮길 때 드러났다. 마스터(기준정보) 테이블처럼 개발에서 정비한 데이터를 운영에 이관하는 작업이 있었는데, 그때 테스트가 쌓아둔 데이터가 함께 딸려 들어갔다. 운영 데이터 속에 정체불명의 테스트 레코드가 섞이는 것이다. 데이터의 신뢰성이 걸린 문제였다.

근본 원인은 격리의 부재였다. 테스트는 독립적이고 반복 가능해야 한다. 그러나 공용 DB를 공유하는 한 실행할 때마다 환경에 흔적이 남았다. 격리가 없으면 테스트는 자기 자신뿐 아니라 그 DB를 쓰는 모든 것에 영향을 준다.

    T[통합 테스트] -->|데이터 적재·잔존| D[(공용 개발 DB)]
    D -->|마스터 데이터 이관| P[(운영 DB)]

접근: 각 테스트에 일회용 DB를

해결 방향은 분명했다. 테스트는 자기만의 격리된 DB에서 돌고, 끝나면 그 DB는 사라져야 한다. 공용 DB를 공유하지 않으면 오염도 없다.

테스트용 DB로는 H2 같은 인메모리 DB가 흔히 쓰인다. 가볍고 빠르지만, 운영이 PostgreSQL이라면 한계가 있다. 인메모리 DB는 PostgreSQL의 고유 함수나 타입, 문법을 완전히 재현하지 못해, 테스트는 통과해도 운영에서 깨질 수 있다. 운영과 다른 환경에서 하는 테스트는 그 자체로 또 다른 위험이다.

그래서 Testcontainers를 택했다. Docker 컨테이너로 운영과 같은 PostgreSQL을 띄우고, 테스트는 그 컨테이너에 붙는다. 테스트가 끝나면 컨테이너는 폐기된다. 운영과 같은 엔진을 쓰면서도 일회용이라는 점이다. 인메모리의 격리와 공용 DB의 사실성을 동시에 얻는 선택이었다.

@SpringBootTest
@Testcontainers
class UserRepositoryTest {

    // 운영과 같은 PostgreSQL을 컨테이너로 띄운다
    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:9.6")
            .withDatabaseName("test");

    // 컨테이너의 접속 정보를 Spring 데이터소스로 주입
    @DynamicPropertySource
    static void datasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}

컨테이너가 뜰 때 포트는 매번 랜덤으로 할당된다. 그래서 접속 URL을 코드에 고정할 수 없고, @DynamicPropertySource로 컨테이너가 실제로 연 포트를 런타임에 받아 Spring에 주입한다. 컨테이너 이미지를 운영과 같은 버전으로 맞추면, 로컬에 그 DB를 깔지 않고도 실제와 같은 환경에서 테스트할 수 있다. 공용 DB라는 외부 의존이 사라진 것이다.

물론 Testcontainers도 공짜는 아니다. 테스트를 돌리는 환경마다 Docker가 필요하다. 로컬에도, CI(지속적 통합) 서버에도. 공용 DB 의존을 Docker 의존으로 바꾼 셈이다. 다만 Docker는 이미 대부분의 개발·CI 환경에 있고, 무엇보다 그 의존은 격리되어 있다. 공용 DB와 달리 누구의 환경도 오염시키지 않는다.

구현: 격리를 어디까지 — Restarted vs Shared

컨테이너로 공용 DB는 떼어냈지만, 질문이 하나 남았다. 컨테이너를 얼마나 자주 새로 만들 것인가. Testcontainers는 두 전략을 준다.

  • Restarted: 테스트 메서드마다 컨테이너를 새로 띄우고 끝나면 내린다. @DirtiesContext로 매 메서드 후 컨텍스트를 초기화해 구현한다. 매 메서드가 깨끗한 DB에서 시작하니 완전한 격리다. 대신 컨테이너를 매번 띄우고 내리는 비용이 크다.
  • Shared: 테스트 클래스가 컨테이너 하나를 공유한다(static 선언). 한 번만 띄우니 빠르지만, 메서드끼리 같은 DB를 본다.

Shared의 간섭은 추상적이지 않다. 코드로 드러난다.

@Test @Order(1)
void 데이터를_하나_넣으면_3건이_된다() {
    jdbc.update("insert into users values (3, 'kim', 'test@example.com')");
    assertThat(userCount()).isEqualTo(3);   // 초기 2건 + 1건 → 통과
}

@Test @Order(2)
void 다음_테스트는_초기_상태를_기대하지만() {
    // 앞 테스트가 넣은 데이터가 그대로 남아 있다
    assertThat(userCount()).isEqualTo(2);   // 기대 2건, 실제 3건 → 실패
}

첫 번째 테스트가 넣은 데이터가 두 번째 테스트에 그대로 남는다. 두 번째 테스트가 초기 상태를 기대하면 실패한다. Shared에서는 테스트 순서와 데이터 누적을 작성자가 직접 책임져야 한다. 매 테스트 전에 데이터를 초기화하거나, 테스트끼리 건드리는 데이터가 겹치지 않게 설계하는 식이다.

나는 Shared를 택했다. 컨테이너를 매 메서드마다 재시작하는 비용보다 테스트 속도가 우선이었기 때문이다. 대신 위 함정을 모르고 들어가지 않았다. Shared의 간섭을 코드로 먼저 확인하고, 테스트끼리 데이터가 충돌하지 않도록 독립성에 주의하며 작성했다. 완전 격리를 포기한 대가로 속도를 얻고, 멱등성은 직접 관리하는 선택이었다.

도입하면서 컨테이너 설정이 테스트 클래스마다 반복되는 것이 보였다. 공통 설정을 커스텀 어노테이션 하나로 묶어, 각 테스트 클래스는 그 어노테이션만 붙이면 컨테이너를 받도록 했다. 설정이 한곳에 모이니 변경도 한곳에서 끝난다.

결과

테스트는 더 이상 공용 DB를 건드리지 않는다. 각 테스트는 격리된 컨테이너에서 돌고 끝나면 사라지니, 테스트 데이터가 개발 DB에 쌓이는 일도, 운영 이관에 딸려 들어가는 일도 없어졌다. 운영과 같은 PostgreSQL에서 검증하므로, 인메모리 DB로 갈아탔을 때처럼 "테스트는 통과하는데 운영에서 깨지는" 위험도 없다. 테스트를 운영에서 떼어내면서, 운영과의 사실성은 지킨 것이다.

부수 효과도 있었다. 테스트가 컨테이너를 스스로 띄우니, 로컬에 DB를 설치하거나 공용 DB 접속 정보를 받아둘 필요가 없어졌다. Docker만 있으면 누구의 환경에서든 같은 테스트가 같은 조건으로 돈다. CI에서도 격리된 컨테이너라 빌드끼리 간섭하지 않는다.

학습

테스트는 운영을 건드리면 안 된다. 당연해 보이지만, 공용 DB를 공유하는 한 테스트는 환경에 흔적을 남긴다. 격리는 선택이 아니라 통합 테스트의 전제다.

격리는 공짜가 아니다. Restarted의 완전한 격리는 속도를 내주고, Shared의 속도는 격리를 내준다. 정답은 없고 제약(테스트 수·CI 시간)에 따라 고른다. 나는 속도를 택했고, 그 대가로 멱등성을 직접 책임졌다.

선택의 비용은 고르기 전에 확인해야 한다. Shared의 간섭은 안 써본 사람에겐 보이지 않는다. 두 번째 테스트가 깨지고 나서야 보인다. 그 함정을 미리 코드로 확인한 것이 Shared라는 선택을 책임 있게 만들었다.
