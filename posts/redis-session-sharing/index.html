문제: 이중화했더니 로그인이 풀린다

고가용성이 요구되는 공공 시스템에서 웹 서버와 WAS(웹 애플리케이션 서버)가 1:1로 묶여 있었다. 웹 1은 WAS 1로만, 웹 2는 WAS 2로만 요청을 보냈다. 서버는 두 벌이었지만 실제로는 서로 건너가지 못하는 경로 두 개였다. WAS 1이 멈추면 웹 1로 들어온 사용자는 그대로 영향을 받았다. 배포하려고 WAS를 내리면 그 경로의 사용자는 배포가 끝날 때까지 기다려야 했다.

그래서 각 웹 서버가 양쪽 WAS로 요청을 보내도록 바꿨다. 바꾸자마자 서버를 오갈 때마다 로그인이 풀린다는 보고가 들어왔다. 세션이 각 WAS의 로컬 메모리에 있었기 때문이다. WAS 1에서 로그인한 사용자의 다음 요청이 WAS 2로 가면, WAS 2에는 그 세션이 없으니 로그인하지 않은 사용자로 처리됐다.

접근: 세션 복제 대 중앙 세션

여러 WAS가 같은 세션을 보게 하는 방법은 두 가지였다. WAS끼리 세션을 복제하거나, 세션을 한 저장소에 두고 모든 WAS가 거기서 읽는 것이다. 나는 저장소를 새로 들이지 않아도 되는 톰캣 세션 클러스터링을 먼저 시도했다. 설정만으로 끝날 수 있다는 점이 끌렸다.

클러스터링을 켠 뒤에도 WAS를 옮겨 다닐 때 로그인이 풀렸다. 나는 원인을 복제 지연으로 봤다. 로그인 직후 세션이 바뀐 순간에 다음 요청이 다른 WAS로 가면, 그 WAS에는 아직 복제가 도착하지 않았다는 판단이었다. 복제를 더 빠르게 맞추는 대신 복제할 필요 자체를 없애기로 하고, 세션을 한곳에 두는 쪽으로 방향을 바꿨다.

저장소는 Redis로 정했다. 세션은 요청마다 읽히니 인메모리 조회가 유리했다. 키마다 유효 기간(TTL, Time To Live)을 걸 수 있다는 점도 세션의 만료 개념과 잘 맞았다. 관계형 DB의 세션 테이블도 후보였고 Spring Session 같은 라이브러리는 JDBC 저장소도 지원하지만, 나는 조회 속도와 TTL 쪽에 무게를 뒀다.

비용도 생긴다. 세션을 읽을 때마다 Redis를 거쳐야 하고, 세션이 한곳에 모인 만큼 Redis가 멈추면 로그인 전체가 멈춘다. Redis의 복제도 기본은 비동기다. 복제본에서 세션을 읽는 구성으로 가면, WAS 사이에서 없앤 복제 지연을 Redis 안에서 다시 만나게 된다.

구현: 세션 분리와 중복 로그인 로직의 분산화

세션 접근 지점을 Redis 조회로 바꾸면서 호출하는 쪽 코드는 최대한 그대로 뒀다. 로컬 메모리에 있던 세션 객체를 외부 저장소에 넣으려면 직렬화할 수 있는 형태로 맞춰야 했고, 기존 코드가 읽고 쓰는 방식과도 호환돼야 했다.

더 까다로운 쪽은 중복 로그인 방지 로직이었다. 같은 계정이 새로 로그인하면 이전 세션을 끊는 정책이었다. 그런데 "이미 로그인해 있는지"는 WAS가 자기 메모리에서 확인하고 있었다. WAS 1은 WAS 2에 누가 로그인해 있는지 모른다. 단일 서버에서 당연했던 가정이 서버가 둘이 되자 에러 하나 없이 틀린 답을 내기 시작했다.

그래서 계정별 활성 세션을 Redis에 기록하고, 새 로그인 때 기존 세션을 지우도록 바꿨다. 이 흐름을 가장 단순하게 옮기면 다음과 같다. 실제 코드가 아니라, 이 설계에 숨은 함정을 보여 주려고 일부러 단순하게 쓴 예제다.

// 로그인 시: 계정당 활성 세션을 기록하고 기존 세션은 끊는다
String prev = redis.get("login:account:" + accountId);
if (prev != null) {
    redis.delete("session:" + prev);
}
redis.set("login:account:" + accountId, newSessionId, SESSION_TTL);
redis.set("session:" + newSessionId, sessionData, SESSION_TTL);

이렇게 쓰면 경합이 일어난다. 같은 계정으로 두 곳에서 거의 동시에 로그인하면 두 요청이 같은 prev를 읽고 각자 새 세션을 저장한다. 이전 세션은 지워지지만 새 세션 두 개가 함께 살아남는다. 막으려던 중복 로그인이 그대로 생긴다. Redis 명령 하나하나가 원자적이라고 해서 이 코드 전체가 한 단위로 실행되는 것은 아니다. 읽기부터 교체까지를 한 단위로 다뤄야 하고, 예를 들어 WATCH 기반 트랜잭션을 쓰면 계정 키가 중간에 바뀌었을 때 처리를 중단하고 재시도할 수 있다. 당시 실제 코드가 이 경합을 어떤 수단으로 막았는지는 기록에 없어서, 여기서는 필요한 처리 단위까지만 적는다.

서버 쪽에서 기존 세션을 지워도, 그 세션으로 이미 화면을 보고 있던 사용자는 아무것도 모른다. 사용자가 요청을 보내지 않으면 서버가 알릴 방법이 없었다. 서버가 상태를 밀어 주는 방식이 더 빠르지만 당시에는 그런 연결을 쓰지 않았으므로, 구현과 운영이 단순한 폴링을 붙였다. 클라이언트가 주기적으로 자기 세션이 유효한지 묻는 방식이다.

클라이언트가 세션 유효성 확인 요청
  → 서버가 세션과 계정의 현재 로그인 상태 확인
  → 무효한 세션이면 로그아웃 안내
  → 클라이언트가 로그인 화면으로 이동

폴링을 쓰면 주기마다 요청이 쌓이고, 세션이 무효화된 뒤 화면이 바뀌기까지 시간이 걸린다. 브라우저가 백그라운드 탭의 타이머를 늦추기 때문에 폴링 주기보다 더 늦어지기도 한다. 그 사이에 오는 요청은 폴링과 상관없이 서버가 인증 단계에서 세션을 확인해 막는다. 폴링은 사용자 화면을 정리하는 역할만 한다.

결과

어느 WAS로 요청이 가든 같은 세션을 읽게 되면서 교차 라우팅 때 로그인이 풀리던 문제가 사라졌다. 중복 로그인 판단도 특정 WAS의 메모리에서 벗어났다.

배포 방식도 달라졌다. 세션이 Redis에 있으니 WAS를 한 대씩 내려 배포해도 사용자 세션이 유지됐다. 한쪽을 배포하는 동안 다른 WAS가 요청을 받아 Redis의 세션을 그대로 썼다. 순차 배포에서 요청까지 잃지 않으려면 세션 말고도 맞출 것이 있다. 배포할 WAS를 트래픽에서 먼저 빼고 처리 중인 요청을 마무리시킨 뒤 내려야 하며, 새 버전이 기존 세션 데이터를 읽을 수 있어야 한다.

학습

웹과 WAS의 고정 매핑을 풀자 각 서버 메모리에 있던 상태가 전부 공유 대상이 됐다. 세션은 로그인이 풀리는 증상으로 바로 드러났다. 반면 중복 로그인 판단은 무력해져도 겉으로 보이는 증상이 없었다. 다음에 라우팅을 바꾼다면 세션 저장 위치보다 로컬 메모리를 읽는 코드부터 전부 찾아 둘 것이다.

버린 대안은 시험한 설정과 함께 남겨야 다시 검토할 수 있다. 톰캣 클러스터 문서를 보면 세션 복제는 동기와 비동기 중에 고를 수 있고 백업 노드 하나에만 복제하는 방식도 있다. 이번 클러스터링 시도는 어떤 모드였는지 남아 있지 않아, 그때의 판단을 지금 다시 따져 볼 수 없었다.

상태를 Redis 한곳에 모으는 일과 그 상태를 동시 요청 속에서 안전하게 바꾸는 일은 별개의 작업이었다. 저장소를 옮기는 동안에는 앞의 일에 시선이 쏠리기 쉽다. 계정별 세션 교체처럼 읽은 값을 보고 다시 쓰는 로직이 있다면, 어떤 단위로 원자적으로 처리할지를 설계 항목에 처음부터 넣어야 한다.
