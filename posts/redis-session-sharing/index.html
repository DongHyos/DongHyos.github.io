문제: 이중화했더니 로그인이 풀린다

고가용성이 요구되는 공공 시스템을 운영하면서 이중화가 되어 있지 않은 구조를 마주했다. 정확히는 웹 서버와 WAS(웹 애플리케이션 서버)가 1:1로 고정돼 있었다. 1번 웹은 1번 WAS로만, 2번 웹은 2번 WAS로만 요청을 보냈다. 서버가 두 벌이라 이중화처럼 보였지만, 실제로는 독립된 두 수직 라인일 뿐이었다. 한 라인이 죽으면 그쪽 사용자는 그대로 영향을 받았고, 배포할 때도 무중단이 불가능했다. 새 버전을 올리려면 WAS를 내려야 했고, 그 라인에 붙은 사용자는 배포가 끝날 때까지 서비스가 끊겼다.

진짜 이중화를 위해 웹 서버가 양쪽 WAS로 교차 라우팅하도록 구성을 바꿨다. 1번 웹의 요청도 2번 WAS로 갈 수 있게 했다. 그러자 곧바로 증상이 보고됐다. 사용자가 서버를 오갈 때마다 로그인이 풀린다는 것이었다.

원인은 세션이었다. 세션은 각 WAS의 로컬 메모리에 저장돼 있었다. 1번 WAS에서 로그인한 사용자가 다음 요청에서 2번 WAS로 라우팅되면, 그쪽에는 세션이 없으니 로그인하지 않은 사용자로 취급됐다. 로컬 세션을 전제로 짠 구조가 교차 라우팅이라는 새 전제와 충돌한 것이다.

graph LR
    W1[웹 1] --> A1[WAS 1
로컬 세션]
    W2[웹 2] --> A2[WAS 2
로컬 세션]

위 구조에서 교차 라우팅을 켜면, 세션이 없는 반대편 WAS로 요청이 흘러가는 순간 로그인이 끊겼다.

sequenceDiagram
    participant U as 사용자
    participant W as 웹(교차 라우팅)
    participant A1 as WAS 1
    participant A2 as WAS 2
    U->>W: 로그인
    W->>A1: 1번 WAS로 라우팅
    A1->>A1: 세션 생성(로컬)
    A1-->>U: 로그인 성공
    U->>W: 다음 요청
    W->>A2: 2번 WAS로 라우팅(교차)
    A2--xU: 세션 없음 → 로그인 풀림

접근: 세션 복제 대 중앙 세션

여러 WAS가 같은 세션을 봐야 한다는 요구는 분명했고, 선택지는 둘이었다. 하나는 WAS끼리 세션을 실시간 복제하는 방식(세션 복제)이고, 다른 하나는 세션을 외부 한 곳에 두고 모든 WAS가 참조하는 방식(중앙 세션)이다.

나는 톰캣 세션 클러스터링을 먼저 시도했다. 별도 저장소 없이 톰캣 설정만으로 세션을 복제할 수 있다는 점이 매력이었다. 그러나 실패했다. 세션 클러스터링은 한 WAS의 세션 변경을 다른 WAS로 밀어 복제하는데, 이 복제는 비동기로 일어난다. 로그인 직후처럼 세션이 막 바뀐 시점에 사용자의 다음 요청이 곧바로 다른 WAS로 라우팅되면, 복제가 도착하기 전이라 그 WAS는 여전히 빈 세션을 봤다. 결국 로그인이 계속 풀렸다. 복제 모델은 노드가 늘수록 동기화 비용이 커지고, 그 지연이 그대로 로그인 풀림으로 드러났다.

그래서 중앙 세션으로 방향을 틀었다. 세션을 한 곳에 두면 복제 지연이라는 문제 자체가 사라진다. 저장소 후보로는 관계형 DB의 세션 테이블도 있었지만, 세션은 수명이 짧고 읽기·쓰기가 잦은 데이터라 디스크 기반 저장소와 맞지 않았다. 나는 Redis를 택했다. 인메모리라 세션 조회가 빠르고, 키 만료(TTL)가 세션 수명 관리와 자연스럽게 맞았기 때문이다.

중앙 세션에도 비용은 있다. 모든 요청이 세션을 외부에서 조회하므로 네트워크 왕복이 한 번 추가되고, 세션을 한 곳에 모은 만큼 그 저장소의 가용성이 중요해진다. 그럼에도 복제 지연으로 로그인이 풀리는 것보다, 빠른 인메모리 조회로 모두가 한 곳을 보게 하는 편이 분명했다.

구현: 세션 분리와 중복 로그인 로직의 분산화

방향이 정해진 뒤에도 손이 가는 부분은 남아 있었다. 기존 로컬 세션을 그대로 옮길 수는 없었다. 로컬 메모리의 세션 객체를 외부 저장소에 담으려면 직렬화 가능한 형태로 맞춰야 했고, 세션을 읽고 쓰는 기존 코드와도 호환을 유지해야 했다. 나는 세션 접근 지점을 Redis 조회로 바꾸되 호출하는 쪽 코드는 최대한 그대로 두며 점진적으로 옮겼다.

진짜 난관은 중복 로그인 방지 로직이었다. 기존 로직은 단일 서버를 전제로 했다. 같은 계정이 이미 로그인해 있으면 기존 세션을 끊는데, 그 "이미 로그인했는지"를 단일 WAS의 로컬 메모리에서 확인했다. 다중 WAS 환경에서는 1번 WAS가 2번 WAS의 세션을 알 수 없으니 이 로직은 무력해진다. 단일 서버에서는 당연하던 가정이 분산되는 순간 소리 없이 무너졌다.

나는 중복 로그인 판단의 기준점을 Redis로 옮겼다. 로그인 시 계정별 활성 세션을 Redis에 기록하고, 같은 계정이 새로 로그인하면 등록된 기존 세션을 무효화했다.

// 로그인 시: 계정당 활성 세션을 Redis에 기록하고 기존 세션은 끊는다
String prevSession = redis.get("login:account:" + accountId);
if (prevSession != null) {
    redis.delete("session:" + prevSession);   // 기존 세션 무효화
}
redis.set("login:account:" + accountId, newSessionId);
redis.set("session:" + newSessionId, sessionData);

남은 문제는 이미 화면을 보고 있는 사용자였다. 다른 곳에서 같은 계정이 로그인하면, 가만히 있던 기존 사용자도 즉시 쫓겨나야 한다. 그러나 사용자가 아무 요청도 보내지 않으면 서버는 세션이 무효화됐다는 사실을 전달할 길이 없다. 나는 클라이언트가 짧은 주기로 서버에 자기 세션의 유효성을 묻고, 무효화됐으면 로그아웃시키는 폴링 방식으로 해결했다.

// 클라이언트가 주기적으로 호출하는 세션 유효성 확인
boolean valid = redis.exists("session:" + currentSessionId);
return valid ? OK : LOGOUT;   // 다른 곳에서 재로그인 시 무효화되어 LOGOUT

폴링은 트레이드오프가 뚜렷한 선택이었다. 주기적 요청이 부하로 쌓이고, 무효화와 실제 로그아웃 사이에 폴링 주기만큼의 지연이 남는다. 서버가 클라이언트로 상태를 미는 방식(push)이 더 즉각적이지만, 당시 환경에서는 구현과 운영의 단순성을 우선해 폴링을 택했다.

    W1 --> A2[WAS 2]
    W2[웹 2] --> A1
    W2 --> A2
    A1 --> R[(Redis

결과

교차 라우팅이 정상 동작했다. 사용자가 어느 WAS로 라우팅되든 세션이 유지됐고, 로그인 풀림 보고가 사라졌다. 한쪽 WAS가 멈춰도 다른 WAS가 같은 세션을 이어받으니 비로소 진짜 이중화가 완성됐다.

가장 큰 부수 효과는 무중단 배포였다. 세션이 Redis에 있으니 WAS를 한 대씩 내려 배포해도 사용자 세션이 살아 있었다. 한 WAS를 내려 배포하는 동안 교차 라우팅이 트래픽을 다른 WAS로 보냈고, 세션은 Redis에 남아 있으니 사용자는 배포가 진행 중인지조차 알 수 없었다. 배포를 위해 서비스 시간을 따로 잡을 필요가 없어졌다. 이중화를 위해 시작한 작업이 배포 방식까지 바꾼 셈이다.

학습

이중화의 본질은 서버 대수가 아니라 상태 공유다. 서버를 두 대로 늘리는 일은 쉽다. 어려운 것은 그 두 대가 같은 상태를 보게 만드는 일이다. 웹-WAS 고정 매핑을 풀면 로컬에 있던 모든 상태가 공유 대상이 된다.

단일 서버를 전제로 짠 로직은 분산 환경에서 조용히 깨진다. 중복 로그인 방지처럼 한 서버 안에서는 당연히 동작하던 로직이, 다중 서버가 되면 무력해진다. 상태에 의존하는 로직은 그 상태가 어디에 있는지부터 점검해야 한다.

먼저 시도해 실패한 대안이 결정의 근거가 됐다. 세션 클러스터링의 실패는 시간 낭비가 아니라 복제 모델의 한계, 곧 동기화 지연을 직접 확인한 과정이었다. 그 실패가 중앙 저장 모델을 택한 분명한 근거가 됐다.
