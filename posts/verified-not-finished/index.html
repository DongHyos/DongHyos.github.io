끝났다고 쓴 글

「느린 쿼리의 두 얼굴」에서 나는 인계받은 사내 업무 시스템의 느린 목록 조회를 다뤘다. 인덱스를 추가했다가 다른 조회의 지연 때문에 되돌리고, 쿼리를 임시 테이블로 분해한 사례다. 선행글의 초기 발행본은 다음 문장으로 판단을 정리했다.

판단의 근거는 둘 다 실행계획이었다. (…) 추측이 아니라 계획을 읽고 갈랐다.

계획은 실제로 읽었다. 다만 확인한 실행의 범위가 좁았다. 초기 발행본에는 쿼리 분해 뒤에도 다른 입력값에서 지연이 남았다는 사실이 빠져 있었다. 그때 이미 관련 계획 캡처를 갖고 있었지만 글을 정리하면서 다시 대조하지 않았다.

이 글은 그 판단을 돌아본 기록이다. 현재 선행글에도 후속 지연과 검증 범위를 반영했으며, 여기서 인용하는 문장은 수정 전 표현이다. 선행글에 있던 추정 비용 ‘약 35→9’도 프로시저 전체의 전후 비교가 아니어서, 전체 성능 개선 수치로 쓰지 않았다.

첫 번째 오판: 검증 환경에서 조회 하나만 확인했다

인덱스를 운영에 반영하기 전에는 개발·테스트 데이터베이스에 먼저 적용하고 대상 조회를 실행했다. 빨라지는 것을 확인했고 운영 반영은 업무가 끝나 사용자가 없는 시간에 했다. 검증 환경을 거쳤고 반영 시점도 골랐다.

그런데 인덱스를 추가하자 같은 테이블을 쓰는 다른 조회들이 느려졌다. 지연이 애플리케이션 타임아웃을 넘겨 해당 화면의 조회가 실패했고, 추가한 인덱스를 되돌렸다. 대상 조회를 개선한 결과만으로 다른 조회에 미치는 영향까지 판단한 것이 문제였다.

인덱스는 특정 조회에만 적용되는 설정이 아니다. 같은 테이블을 사용하는 다른 쿼리에도 접근 경로를 제공하며 데이터 변경 시 유지 비용이 든다. 다만 모든 쿼리의 계획이 반드시 바뀐다는 뜻은 아니다. 당시 확인한 장애의 원인을 각 조회의 조인 순서나 특정 연산 하나로 단정할 근거도 충분하지 않다.

검증 환경에서는 다른 프로시저를 실행하지 않았다. 반영 전에 관련 조회를 확인할 환경이 있었는데도 대상 조회 하나만 보고 넘어갔다. 사용자 없는 시간을 골랐다는 사실이 빠진 검증을 대신해 주지는 못했다.

두 번째 오판: 같은 값으로 비교한 한 번의 실행

인덱스를 되돌린 뒤에는 쿼리를 분해했다. 후보 키를 임시 테이블 #cand에 먼저 담고 그 집합에 나머지 데이터를 연결하는 방식이다. 관리 도구에서 원본과 분해한 쿼리에 같은 파라미터 값을 넣고, 실행 시간과 실행계획을 나란히 비교했다.

수백 밀리초 수준으로 줄어든 실행이 있었고 화면에서도 개선을 확인했다. 나는 여기서 끝났다고 판단했다. 선행글의 초기 발행본에는 이렇게 썼다.

무엇보다 이 변경은 프로시저 하나에 갇혀 있어서 다른 조회를 건드리지 않았다. 되돌리기도 쉬웠다.

수정한 코드의 범위는 프로시저 안이었다. 하지만 CPU나 tempdb 같은 자원까지 다른 조회와 분리된 것은 아니었다. 무엇보다 그 프로시저 자체도 입력값에 따라 실행 시간이 달랐다.

사용자로부터 여전히 느리다는 신고를 받은 뒤 캐시된 계획의 실행 통계를 확인했다. 당시에는 느린 실행과 관련된 계획의 재사용을 의심하는 근거로 삼았다. 다만 캐시 통계를 개별 요청의 전체 실행 이력으로 읽어서는 안 된다. 예를 들어 SQL Server의 sys.dm_exec_query_stats는 캐시에 남은 계획의 완료된 실행을 집계하며, 계획이 제거되면 관련 통계도 사라진다. 빠른 실행이 조회 결과에서 보이지 않는다는 사실만으로 그 실행이 없었다고 결론 낼 수는 없다. (실행 통계의 범위)

계획 두 장에서 확인한 것과 추론한 것

남아 있는 두 실행계획에서 같은 중간 결과 적재 문장(SELECT INTO)을 비교했다. 아래 수치는 그 문장의 기록이다. 프로시저 전체나 애플리케이션 요청 전체의 응답 시간이 아니다.

항목 실행 A 실행 B
SQL 문장·쿼리 해시·계획 해시 동일 동일
캐시에서 계획을 가져왔는가 예 예
컴파일 값과 실행 값 비교 기록된 파라미터 17개 모두 일치 17개 중 3개 불일치
해당 문장의 추정 행 수 1행 1행
실제 적재 행 수 36행 1,951행
tempdb spill 경고 없음 있음
문장 경과 시간 486ms 6,578ms

이 문장의 경과 시간은 약 13.5배 차이 난다. B에서는 추정 행 수와 실제 행 수의 차이가 크고 spill 경고도 나타났다. spill은 정렬·해시 작업 등의 중간 데이터를 메모리에 모두 담지 못해 tempdb로 내보내는 현상이다. 이를 해석할 때는 행 수뿐 아니라 연산별 메모리 사용과 할당도 함께 봐야 한다. 경고가 있다는 사실만으로 지연 전부를 설명할 수는 없다. (메모리 할당과 spill 진단)

두 캡처의 CompileTime 값도 같지만 이는 컴파일에 걸린 시간이지 컴파일한 시각이 아니다. 계획 해시가 같다는 사실 역시 같은 캐시 항목이나 같은 컴파일 사건을 증명하지 않는다. 동일한 해시를 갖는 별도 캐시 항목도 있을 수 있다. 따라서 “컴파일까지 같고 다른 것은 파라미터뿐”이라고 단정했던 설명은 범위를 넘었다. (계획 식별과 캐시 재사용)

확인된 것은 같은 문장과 계획 해시에서 입력값, 처리 행 수, spill 여부와 시간이 달랐다는 점이다. 이는 컴파일 때 참고한 값에 맞는 계획을 다른 값에도 재사용하는 파라미터 민감도 문제를 의심할 근거다. 하지만 두 캡처만으로 당시 동시 부하나 대기 상태까지 같았다고 볼 수는 없다. 컴파일 값과 실행 값이 다르다는 사실 자체가 항상 문제인 것도 아니다. 문제는 재사용한 계획이 다른 입력에서도 적절한가에 있다.

원본과 분해한 쿼리에 같은 값을 넣은 비교는 그 값에서의 개선을 확인하는 데 유효했다. 빠진 것은 다른 값에서도 같은 효과가 나는지 보는 과정이었다. 첫 번째에는 다른 조회를, 두 번째에는 다른 입력값을 검증 범위에서 놓쳤다.

재컴파일을 선택한 뒤에도 남은 검증

후속 조치는 실행할 때 계획을 다시 만들도록 하는 것이었다. 다만 남아 있는 기록만으로는 당시 재컴파일을 문장 단위와 프로시저 단위 중 어디에 적용했는지 확정할 수 없다. 두 방식의 범위와 비용은 구분해야 한다.

SQL Server의 문장 단위 OPTION (RECOMPILE)은 현재 값을 사용해 임시 계획을 만들고 실행 후 버린다. 프로시저 전체를 재컴파일하는 방식보다 적용 범위를 좁힐 수 있다. 재컴파일은 새로운 계획을 만들 기회를 주지만, 언제나 더 빠른 계획이나 정확한 행 수 추정을 보장하지는 않는다. 실행할 때마다 컴파일 비용도 추가된다. (재컴파일 방식과 범위, RECOMPILE 힌트)

반영 후에는 시간대를 나눠 CPU 사용량을 관찰했다. 피크 시간에도 부담이 크지 않다고 판단해 변경을 유지했다. 앞선 검증보다 관찰 시간대는 넓혔지만, 이는 CPU 부담을 살핀 결과다. 여러 파라미터 조합의 응답 시간을 검증한 결과와 같지는 않다.

화면이 바로 열린다는 개선은 확인했다. 그러나 애플리케이션 경로의 응답 시간을 수치로 남기지 않았다. CPU 관찰만으로 컴파일 비용을 정확히 분리해 측정한 것도 아니다. 따라서 후속 조치의 결과는 당시의 화면 확인과 CPU 관찰 범위까지로 적는다.

완료를 판단할 때 남겨야 할 것

지금은 인덱스를 반영하기 전에 같은 테이블을 사용하는 관련 프로시저와 조회 쿼리를 먼저 모아 영향도를 살핀다. 첫 번째 실패 뒤 실제로 바꾼 절차다. 다만 목록을 만들었다는 사실만으로 동적 SQL이나 애플리케이션에서 직접 실행하는 쿼리까지 모두 확인했다고 볼 수는 없다.

입력값의 표본을 고르는 절차는 아직 그만큼 정리하지 못했다. 다음 검증에서는 결과가 적은 값과 많은 값, 자주 쓰는 조건과 드문 조건을 나눠 볼 필요가 있다. 각 경우의 결과 동등성, 문장별 실행 시간과 전체 요청 시간, 논리적 읽기·CPU·spill을 함께 남기는 것이 보완할 과제다. 이 항목들을 당시 모두 측정했다고 쓰지는 않는다.

두 번의 실패에서 빠른 실행 자체가 거짓이었던 것은 아니다. 그 실행 하나의 결과를 다른 조회와 입력값에도 적용한 판단이 잘못됐다. 이제 완료를 설명할 때는 무엇을 바꿨는지에 더해 어떤 조회·값·호출 경로에서 확인했고, 무엇을 아직 측정하지 않았는지 함께 남기려 한다.
