주문이 접수됐는지 알 수 없을 때

이전 글에서는 언어 모델을 매매 코어 밖에 두고 규칙 승인과 주문 실행 경로를 나눴다. 이번에는 주문 요청이 실패하거나 결과를 확인하지 못했을 때 케이지가 어떻게 대응하는지 살펴본다.

매수 주문을 POST로 보낸 뒤 타임아웃이 났다고 하자. 증권사에 도착하지 않았을 수도 있고, 접수됐지만 응답을 받지 못했을 수도 있다. 곧바로 재전송하면 중복 주문이 될 수 있다. 전송을 멈추면 매수 기회를 놓칠 수 있지만, 나는 이 프로젝트에서 기회 손실보다 오발주 회피를 우선했다.

그래서 엔진의 주문을 SafetyCage.submit으로 모았다. 케이지는 입력, 실행 모드, 중지 설정, 허용 종목, 한도와 중복 여부를 검사한 뒤 게이트웨이를 호출한다. 이는 프로젝트에서 정한 호출 경로다. 같은 프로세스의 다른 코드가 게이트웨이를 직접 호출하지 못하도록 권한까지 격리한 구조는 아니다.

실행 전에 기록한다

실주문 모드인 LIVE에서 검사를 통과하면 다음 순서로 진행한다. 아래는 집행 함수의 주요 단계이며, 예외 처리와 누적 한도 갱신은 생략했다.

멱등키 예약 + INTENT 주문 생성 (같은 DB 트랜잭션)
→ 감사 기록 저장 (별도 DB)
→ CAGED 저장
→ 게이트웨이 주문 호출
→ SENT 저장
→ 응답에 따른 상태 저장

감사 기록에는 주문 키, 주문을 낸 규칙, 근거 참조, 검사 결과의 스냅샷을 담는다. 이 기록이 실패하면 게이트웨이를 호출하지 않는다. 실행 전에 기록하는 audit-before-act 방식이다. 테스트에서도 감사 저장 실패를 주입했을 때 주문 호출이 0회인지 확인했다.

이 기록은 주문을 시도한 이유를 추적하기 위한 것이며, 접수나 체결의 증거는 아니다. 멱등키 예약과 감사 저장도 별도 트랜잭션이라 감사 저장이 실패하면 예약된 키와 INTENT 행이 남는다. 같은 키로 다시 제출해도 중복으로 차단되므로 이후 정리가 필요하다.

더 중요한 틈은 외부 주문과 로컬 상태 저장 사이에 있다. 이 구현은 게이트웨이 호출이 돌아온 뒤 SENT를 저장한다. 증권사가 주문을 접수한 직후 프로세스가 종료되면 로컬에는 CAGED가 남을 수 있다. 따라서 CAGED라는 이유만으로 미전송을 확정해서는 안 된다. 실행 전 기록은 복구 단서를 남기지만, 증권사와 로컬 데이터베이스를 하나의 트랜잭션으로 만들지는 못한다.

같은 키의 재제출을 차단한다

진입 주문의 키는 E-{규칙ID}-{거래일} 형태다. 같은 규칙이 같은 날 반복해서 조건을 충족해도 같은 키를 사용한다. 주기적으로 조건을 평가하는 엔진이 동일한 진입 주문을 거듭 제출하는 상황을 막기 위한 선택이다.

케이지의 사전 조회만으로는 동시 제출을 막을 수 없다. 두 요청이 모두 “기존 주문 없음”을 읽을 수 있기 때문이다. 그래서 상태 저장소는 client_order_id를 기본키로 예약하고, 키 예약과 주문 행 생성을 한 트랜잭션에서 처리한다. 같은 키가 충돌하면 새 주문을 만들지 않는다. 감사 로그의 기본키와 허용된 상태 전이 검사도 중복 진행을 막는 방어로 둔다.

보장 범위는 같은 상태 데이터베이스에 키가 보존되는 동안이다. 별도 데이터베이스에서 실행하거나 다른 키를 만들면 같은 경제적 의미의 주문이라도 이 장치로 막을 수 없다. 예약 후 전송에 실패한 요청까지 재제출을 차단하는 비용도 있다. 따라서 이를 “주문이 반드시 정확히 한 번 실행된다”는 보장으로 설명하면 안 된다.

검수 중 오류 분류의 한계도 확인했다. 예약 함수는 sqlite3.IntegrityError를 모두 중복으로 취급한다. 하지만 이 예외에는 NOT NULL 위반도 포함된다. 케이지의 입력 검사가 앞에 있더라도 저장소에서는 기본키 충돌과 다른 무결성 오류를 구분하는 편이 원인 추적에 정확하다.

타임아웃 뒤에는 재전송 대신 조회한다

게이트웨이는 주문 전송 중 TransportTimeout이 발생하면 같은 clientOrderId로 주문을 조회한다. 아래는 조회 결과 처리 부분이다. 타입과 예외 정의는 생략했으며, 발견한 주문의 상태를 해석하는 한계도 그대로 남긴 발췌다.

def _recover_by_status_query(self, client_order_id):
    try:
        order = self.get_order_by_client_id(client_order_id)
    except TransportTimeout:
        return OrderAck(client_order_id, status="UNKNOWN")

    if order is None:
        # 조회에서 못 찾았다는 사실만으로 미전송을 확정하지 않는다.
        return OrderAck(client_order_id, status="UNKNOWN")

    # 이 구현은 발견한 기록의 실제 주문 상태를 구분하지 않는다.
    return OrderAck(
        client_order_id,
        status="ACCEPTED",
        toss_order_id=order.get("orderId"),
    )

조회에서 주문을 찾지 못하거나 조회 자체가 타임아웃이면 UNKNOWN을 반환한다. 미전송이나 실패로 확정하지 않고 주문 POST도 다시 보내지 않는다. 이후 증권사 주문·체결 내역과 로컬 기록을 대조하는 정합성 확인 절차(reconcile)가 필요하다. 이 절차에서도 증거가 부족하면 미확정 상태가 남을 수 있다.

반대로 주문을 찾으면 이 함수는 실제 상태와 관계없이 ACCEPTED로 분류한다. 따라서 여기서의 ACCEPTED는 체결 확정을 뜻하지 않으며, 취소·거절 등 실제 주문 상태를 그대로 반영한다는 보장도 없다. 조회 중 타임아웃 외 예외는 상위 케이지로 전달된다. 케이지는 이를 받아 UNKNOWN 전이를 시도하지만 상태 저장 자체의 실패까지 모두 흡수하지는 않는다.

HTTP 429는 별도 경로다. 구현은 Retry-After를 반영해 횟수를 제한하여 같은 요청을 재시도한다. 다만 429가 뜻하는 것은 요청 빈도 제한이며, 그 상태 코드만으로 주문이 실행되지 않았다고 단정할 수는 없다. POST 재시도의 안전성은 증권사 API의 멱등성 계약이나 최초 요청이 적용되지 않았다는 근거에 달려 있다. 429 정의와 HTTP 재시도 원칙을 기준으로도 둘은 구분해야 한다.

테스트로 확인한 것과 남은 범위

이번 검수에서는 로컬 소스의 케이지·게이트웨이·상태 저장소·감사 로그·주문 파이프라인 테스트 140개를 임시 복사본에서 실행했다. 외부 통신을 막고 가짜 게이트웨이·전송 객체와 임시 데이터베이스를 사용했으며 모두 통과했다. 확인한 핵심 동작은 다음과 같다.

  • 같은 키의 재제출과 동시 예약에서 중복 생성을 차단한다.
  • 감사 기록 실패 시 주문을 보내지 않는다.
  • 주문 타임아웃 뒤에는 POST를 반복하지 않고 상태를 조회한다.
  • 주문 미발견과 조회 타임아웃을 UNKNOWN으로 남긴다.
  • SHADOW와 DRY에서는 게이트웨이 주문 호출이 없다.

SHADOW와 DRY의 차이도 범위를 좁혀 설명해야 한다. 확인한 케이지 구현에서는 두 모드 모두 같은 검사를 거쳐 판정만 반환한다. 키 예약, 감사 기록, 주문 호출은 수행하지 않으며 DRY에만 있는 별도의 주문 형식 검증 단계도 없다. 기본값은 SHADOW지만, 이 경로만 실행해서 LIVE의 예약·감사·전송 순서를 검증할 수는 없다. 해당 순서는 가짜 게이트웨이를 연결한 LIVE 테스트에서 확인했다.

이 결과는 현재 확인 가능한 소스와 테스트의 범위다. 최초 발행 시점의 전체 실행 결과나 실거래 중복률, 수익을 입증하는 수치는 아니다. 추가 재현에서는 주문 호출 뒤 종료하면 CAGED가 남는 상황과, 조회에서 거절된 주문을 찾아도 ACCEPTED로 분류하는 동작을 확인했다.

학습

케이지를 만들며 얻은 기준은 확인하지 못한 결과를 성공이나 실패로 서둘러 확정하지 않는 것이다. 멱등키는 같은 요청의 재제출을 막고, 감사 기록은 실행 이유를 남기며, 상태 조회는 응답을 받지 못한 주문의 단서를 찾는다. 각 장치는 서로 다른 문제를 다룬다.

그 경계도 함께 기록해야 한다. 로컬 상태만으로 외부 실행 여부를 단정하지 않고, 조회에서 찾은 주문은 실제 상태를 해석해야 한다. 재시도 정책에는 상태 코드뿐 아니라 상대 API의 계약이 필요하다. 주문이나 결제를 자동화할 때는 정상 응답 처리와 함께, 결과를 확인할 수 없을 때 무엇을 보류하고 어떤 증거로 다시 판단할지 정해야 한다.
