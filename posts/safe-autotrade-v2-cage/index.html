비가역 작업에서 진짜 위험한 건 실패가 아니라 모호함

이전 글에서 나는 LLM을 매매 코어 밖으로 밀어내고, 모든 주문이 케이지라는 단일 관문을 통과하게 했다. 이 글은 그 케이지 안을 판다. LLM이 사라진 자리에서도 여전히 어려운 문제가 남기 때문이다. 비가역성이다.

주문 하나를 예로 들자. 토스 API로 매수 주문을 POST했는데, 응답이 오지 않는다. 네트워크가 끊겼거나 타임아웃이 났다. 이때 시스템은 답할 수 없는 질문 앞에 선다. 주문이 들어갔나, 안 들어갔나? 재전송하면 이미 체결된 주문을 한 번 더 내서 돈이 두 배로 나갈 수 있다. 재전송하지 않으면 아직 안 들어간 주문을 영영 놓칠 수 있다.

여기서 배운 것은, 비가역 작업에서 최악은 실패가 아니라 모호함이라는 점이다. 실패는 알면 대응한다. 하지만 "나갔는지 모르는 상태"는 대응 자체가 도박이 된다. 자동매매가 무서운 이유는 봇이 틀린 판단을 해서가 아니라, 이 모호한 순간에 봇이 아무 행동이나 할 수 있어서다.

접근: 제1원칙을 코드로 강제하는 단일 관문

그래서 나는 시스템의 헌법 1조를 수익이 아니라 오발주 회피로 정했다. "틀린 행동보다 무행동이 낫다. 의심스러우면 멈춘다." 놓친 기회는 아프지만 회복되고, 잘못 나간 주문은 회복되지 않는다. 이 비대칭이 원칙의 근거다.

문제는 이런 원칙을 주석이나 프롬프트에 적어두면 지켜지지 않는다는 것이다(1편의 교훈과 같다). 원칙은 구조가 되어야 한다. 케이지는 모든 주문이 예외 없이 통과하는 단일 관문이고, 엔진조차 게이트웨이를 직접 참조하지 못한다. 주문은 오직 케이지의 submit으로만 나간다. 그러니 이 관문 하나에 방어를 심으면, 시스템의 어떤 경로로 온 주문이든 그 방어를 우회할 수 없다.

케이지가 비가역성을 다루는 방식은 제1원칙의 세 가지 얼굴로 나타난다.

실행 전에 기록한다 (audit-before-act)

첫째, 케이지는 실주문을 보내기 전에 그 주문의 꼬리표를 먼저 남긴다. 어느 규칙이 이 주문을 냈는지, 근거가 무엇인지를 감사 로그에 기록하고, 그 기록이 성공해야만 게이트웨이를 호출한다.

def _execute_live(self, intent, verdict):
    # 1) 멱등 예약 — 이미 있는 키면 fresh=False → 중복으로 거부
    reservation = self._state.reserve_client_order_id(intent.client_order_id, ...)
    if not reservation.fresh:
        return Verdict(False, verdict.effective_mode, RejectReason.DUP_KEY)

    # 2) audit-before-act — 게이트웨이를 부르기 *전에* 꼬리표를 남긴다.
    #    기록이 실패하면 주문을 보류한다(게이트웨이 미호출 = 꼬리표 없는 거래 0).
    try:
        self._audit.record_execution(AuditRecord(
            client_order_id=intent.client_order_id,
            trigger_rule_id=intent.source_rule_id,  # 어느 규칙이 이 주문을 냈나
            basis_refs=list(intent.basis_refs),
        ))
    except AuditError:
        return Verdict(False, verdict.effective_mode, RejectReason.UNKNOWN_STATE)

    # 3) 여기까지 통과해야 비로소 실주문을 보낸다.
    ack = self._gateway.place_order(...)

순서가 핵심이다. 데이터베이스의 write-ahead 로그와 같은 발상이다. 되돌릴 수 없는 행동을 하기 전에, 그 행동의 흔적을 먼저 되돌릴 수 있는 곳(로그)에 남긴다. 감사 기록이 실패하면 주문은 아예 나가지 않는다. 그래서 꼬리표 없는 체결은 구조적으로 0건이다. 모든 실주문에는 그것을 낳은 규칙과 근거가 반드시 대응한다. 나중에 "이 주문 왜 나갔지?"라고 물었을 때 답이 없는 경우가 생기지 않는다.

같은 일을 두 번 하지 않는다 (멱등)

둘째, 모든 주문에는 멱등키가 붙는다. 진입 주문의 키는 E-{규칙ID}-{거래일} 형태로, 같은 규칙이 같은 날 조건을 여러 번 충족해도 항상 같은 키가 나온다. 엔진은 5초마다 폴링하며 조건을 재평가하므로, 멱등키가 없으면 한 번 사고 싶은 종목을 폴링 주기마다 반복해서 살 수도 있다.

키는 clientOrderId를 기본키로 하는 테이블에 예약된다. 같은 키를 두 번 넣으면 데이터베이스가 UNIQUE 제약으로 충돌을 일으키고, 이때 새 주문을 만드는 대신 "이미 있음"을 반환한다.

def reserve_client_order_id(self, client_order_id, ...) -> Reservation:
    try:
        with self._conn:  # 키 예약과 주문 생성을 한 트랜잭션으로
            self._conn.execute(
                "INSERT INTO idempotency_keys (client_order_id, reserved_at) VALUES (?, ?)",
                (client_order_id, now))
            self._conn.execute("INSERT INTO orders (...) VALUES (...)", (...))
    except sqlite3.IntegrityError:
        # 이미 예약된 키 → 새 주문을 만들지 않고 '기존'을 반환(멱등)
        return Reservation(fresh=False, order_ref=client_order_id)
    return Reservation(fresh=True, order_ref=client_order_id)

이 멱등성은 한 겹이 아니라 여러 겹으로 막혀 있다. 케이지가 제출 전에 중복을 조회하고, 그걸 지나쳐도 이 예약의 UNIQUE 제약이 막고, 감사 로그도 같은 키의 중복 기록을 거부하며, 주문 상태 기계도 이미 전송된 주문을 다시 전송 단계로 되돌리는 전이를 불법으로 막는다. 테스트에서 이 겹들을 한 번에 하나씩 무력화해봤을 때는 중복 주문이 뚫리지 않았다. 네 겹을 동시에 부러뜨려야 비로소 중복이 새어나갔다. 방어는 한 줄이 아니라 깊이로 세우는 편이 안전하다.

모르면 되묻는다 (타임아웃 복구)

셋째, 앞에서 말한 그 모호한 순간, 주문을 POST했는데 응답이 오지 않는 경우다. 케이지 아래 게이트웨이는 이때 재전송하지 않는다. 대신 토스에 되묻는다. "방금 그 주문, 정말 들어갔나?"

def _submit_order(self, path, payload, client_order_id) -> OrderAck:
    try:
        resp = self._send_json(req)          # 주문 POST
    except TransportTimeout:
        # 응답 분실 → 재전송하면 중복 위험. 재시도 대신 '들어갔는지'를 되묻는다.
        return self._recover_by_status_query(client_order_id)
    return self._order_ack(client_order_id, resp)

def _recover_by_status_query(self, client_order_id) -> OrderAck:
    try:
        order = self.get_order_by_client_id(client_order_id)  # GET /orders 상태조회
    except TransportTimeout:
        return OrderAck(client_order_id, status="UNKNOWN")    # 조회마저 실패 → 모름
    if order is None:                                         # 주문이 실재하지 않음
        return OrderAck(client_order_id, status="UNKNOWN")    # 모르면 UNKNOWN, 함부로 안 움직임
    return OrderAck(client_order_id, status="ACCEPTED", toss_order_id=order.get("orderId"))

상태조회로 주문이 실재하면 그 결과를 받아들이고, 없거나 조회마저 타임아웃이면 UNKNOWN으로 표시한다. UNKNOWN은 "실패"가 아니라 "모른다"는 정직한 상태다. 함부로 재주문하거나 성공으로 간주하지 않고, 나중에 계좌와 대조하는 정리 절차(reconcile)로 해소한다. 참고로 429(rate limit)는 다르게 다룬다. 429는 응답을 받은 상태라 주문이 안 나간 게 확실하므로 재시도가 안전하다. 응답을 못 받은 타임아웃만 "모르는 상태"로 취급한다. 재시도해도 되는 실패와 그러면 안 되는 모호함을 가르는 것이 요점이다.

결과: 방어를 점진적으로 신뢰한다

이 세 방어의 값어치는 측정으로 확인된다. 같은 규칙이 폴링마다 반복 충족돼도 중복 주문은 0이고, 실주문 중 감사 꼬리표가 없는 것은 0이며, 타임아웃은 크래시나 중복 없이 UNKNOWN으로 흡수된다. 앞서 말했듯 멱등의 네 겹은 하나씩 무력화해선 뚫리지 않았다.

그런데 이 방어가 실제로 작동하는지는 어떻게 믿나. 나는 한 번에 실탄을 맡기지 않고 믿음의 사다리를 뒀다. 시스템은 세 모드로 돈다. SHADOW는 판단만 기록하고 실주문을 내지 않고, DRY는 주문 형식까지 검증하되 전송하지 않으며, LIVE만 실주문을 낸다. 기본값은 SHADOW다. 각 칸에서 트리거가 의도대로 발화하는지, 멱등키와 꼬리표가 제대로 붙는지를 확인한 뒤에야 다음 칸으로 올라간다. 금액 한도도 낮게 시작해 신뢰가 쌓이는 만큼 점진적으로 올린다. 지금 이 시스템은 SHADOW에 있고, 그래서 이 글은 수익이 아니라 구조를 말한다.

학습

첫째, 비가역 작업의 방어는 실패를 없애는 게 아니라 모호함을 최악으로 가정하는 것이다. 네트워크는 끊기고 응답은 분실된다. 그 사실을 없앨 수는 없다. 할 수 있는 건 "모르는 상태"에 빠졌을 때 시스템이 가장 안전한 쪽(멈춤, 되묻기, UNKNOWN 표시)을 택하도록 미리 정해두는 것이다.

둘째, 되돌릴 수 없는 행동은 되돌릴 수 있는 흔적을 앞세운다. audit-before-act도, 멱등키 예약도, 타임아웃 시 상태조회도 전부 같은 형태다. 비가역 행동 앞에 "이미 했는가", "정말 나갔는가"를 확인할 수 있는 가역적 기록을 먼저 세운다. 데이터베이스가 write-ahead 로그로 하는 일을, 주문 파이프라인에서 다시 한다.

셋째, 이 패턴은 자동매매만의 것이 아니다. 결제 요청에 멱등키를 붙이는 것, 배포 스크립트가 실행 전에 상태를 스냅샷하는 것, 삭제 API가 재시도에 안전하도록 설계되는 것. 전부 "되돌릴 수 없는 작업을, 모호한 실패 앞에서도 안전하게" 만드는 같은 문제다. 그리고 그 안전은 사후에 덧붙이기 어렵다. 관문을 하나로 모으고 그 관문에 방어를 심는 것은, 대개 처음 설계할 때만 값싸게 할 수 있는 일이다.
